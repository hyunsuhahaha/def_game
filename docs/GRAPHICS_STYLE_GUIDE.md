# 모든 그래픽 작업의 필수 기준 — 현재 적용된 카툰 픽셀 스타일

**이 문서는 선택적 참고 자료가 아니라 앞으로의 모든 그래픽 제작·수정·교체에 적용하는 프로젝트 규칙이다. 사용자 요청: “앞으로 모든 그래픽작업에 이 그래픽을 … 알아먹을수있게 설명해주는 문서”. 기준은 아래에 지정한 현재 v3 그래픽이다.**

**한 문장: 큰 형태는 단순하게, 그 형태 안의 픽셀 명암은 정교하게, 게임 화면에서는 작아도 무엇인지 바로 알아보이게 만든다.**

캐릭터·몬스터·보스·나무·지형·건물·장비·아이콘·투사체·불·연기·기타 FX에 모두 적용한다. 새 지역이나 다른 재질도 같은 표현 원리를 따른다. 모든 대상을 숲 색으로 칠하거나 같은 크기로 만들라는 뜻은 아니다. 이 문서를 추가했다고 기존 자산 전체를 임의로 교체할 권한이 생기지는 않는다. 작업 요청 범위 안에서 적용한다.

## 0. 작업 시작 전에 반드시 할 일

**지역 맵·생물 작업은 [생태 조사와 지역별 적 규칙](BIOME_ECOLOGY.md)도 읽는다.** 지형 색만 바꾸지 말고 대표 식생의 실루엣·생물·서식 위치로 장소를 구분한다. 현실 생태와 게임용 과장을 구분하고, 환경용 생물을 전투 적 구현 완료로 보고하지 않는다.

**대표 나무 한 종의 크기 변형으로 숲을 채우지 않는다.** [혼합 식생 규칙](BIOME_VEGETATION.md)에 따라 지역별 큰 식물 최소 3종과 하층 식물을 구분한다. 단순한 카툰 덩어리를 유지한 채 수관·줄기·뿌리의 실루엣으로 수종을 구별한다.

**윤곽 가독성:** 사용자는 외곽선을 선명하게 하는 방향을 제안한 뒤 최종 굵기는 제작자가 판단하도록 맡겼다. 고정 픽셀 수를 사용자 명령으로 취급하지 않는다. 새 지역 자산의 출발점은 짙은 유색 내부 윤곽(나무 약 2픽셀, 작은 환경 생물 약 3픽셀)이지만 기본 줌에서 배경과의 분리·단순한 카툰 형태를 보고 조정한다. 내부 명암을 모두 검정 선으로 나누지 않고 알파·발선을 유지한다. 실루엣이 검정 덩어리가 되면 선을 줄인다.

1. 아래 **실제 적용 화면과 자산 보드 이미지를 열어 본다.** 파일 이름만 읽고 스타일을 이해했다고 판단하지 않는다.
2. 작업할 대상과 가장 가까운 기준 자산을 하나 고른다. 예: 작은 동물 → 멧돼지/다람쥐, 나무 → 나무 4종, 소품 재질 → 담배.
3. 이 문서의 제작 규격과 마지막 체크리스트를 읽는다.
4. 기준 이미지에 접근할 수 없다면 그 사실을 알린다. 기억 속 “뱀서풍”, “인디풍”, “고퀄”을 대신 적용하지 않는다.

사용자의 새 명시적 지시가 우선한다. 이 문서는 **원하는 외형**, [PIXEL_ART_PIPELINE.md](PIXEL_ART_PIPELINE.md)는 **기술·품질 요구**, [FOREST_ARCADE_ART.md](FOREST_ARCADE_ART.md)는 **현재 v3 구현 기록**이다. 기술 문서의 “고밀도”를 실사풍으로 해석해서 외형 기준을 뒤집지 않는다. 해결되지 않는 충돌은 임의로 고르지 말고 확인한다.

## 2. 그림을 말로 풀어 설명하면

### 큰 형태: 멀리서도 읽히는 간단한 덩어리

나무는 수백 장의 잎이 먼저 보이면 안 된다. 둥근 잎 덩어리 몇 개, 그 아래 줄기, 바닥에 닿는 뿌리가 먼저 보여야 한다. 소나무는 층층이 내려오는 삼각형 덩어리, 자작나무는 밝고 가느다란 갈라진 줄기로 구분한다.

멧돼지는 넓고 낮은 갈색 몸, 작은 다리, 작은 엄니가 핵심이다. 다람쥐는 작은 주황색 몸과 올라간 꼬리가 핵심이다. 버섯은 큰 갓과 짧은 줄기다. 새 몬스터도 “몸 덩어리 + 한두 가지 식별 특징”부터 만든다. 전체 모습보다 갑옷·보석·깃털·이빨·털의 수가 먼저 눈에 들어오면 방향이 잘못된 것이다.

### 내부 묘사: 단순한 덩어리 안에 깊이를 넣는다

잎 덩어리 하나에도 밝은 윗면, 중간 면, 어두운 아랫면이 있다. 줄기에는 방향을 따라 흐르는 몇 갈래의 명암이 있다. 멧돼지의 이마·코·엄니는 밝기와 재질이 다르다. **단순한 모양이라는 이유로 내부를 한 색으로 채우지 않는다.**

반대로 모든 표면을 잔점으로 덮지 않는다. 밝기 변화는 둥근 면·접힌 면·겹치는 면을 설명해야 한다. 어떤 면을 설명하는지 말할 수 없는 노이즈는 세부 묘사로 인정하지 않는다.

### 분위기: 작은 인디 액션 게임의 선명한 픽셀

살짝 과장한 비율, 확실한 표정, 재질에 따른 단계별 명암을 사용한다. 사진·3D 렌더·매끈한 모바일 벡터 그림·복잡한 판타지 일러스트처럼 보이면 안 된다. “뱀서 느낌”은 군집 전투에서의 가독성과 간결한 형태를 설명하는 말이다. 다른 게임 자산을 복사하거나 일부러 저해상도로 퇴보시키라는 뜻이 아니다.

## 4. 픽셀·해상도·명암의 제작 규칙

**원생 픽셀**은 최종 스프라이트가 실제로 가진 픽셀이다. 16×16을 nearest로 128×128로 키우면 여전히 16×16 수준의 정보다. 투명 여백을 늘리거나 PNG를 4K로 저장해도 디테일이 늘지 않는다.

**픽셀 클러스터**는 같은 면을 설명하는 붙어 있는 픽셀 덩어리다. 잎 덩어리의 밝은 윗면처럼 의미가 있어야 한다. **색상 램프**는 같은 재질의 그림자부터 밝은 부분까지 순서대로 정한 색 목록이다. **디더링**은 두 단계 사이를 규칙적인 픽셀 배치로 연결하는 방법이며 무작위 점 뿌리기가 아니다.

- 최종 표시 크기를 먼저 정한 뒤 제작 그리드를 고른다. 고해상도 원화를 게임에서 임의로 축소하는 것을 픽셀 제작 과정으로 대신하지 않는다. 제작 단계에서 고정 그리드·재질 램프·윤곽·앵커를 정리한다.
- 명암은 위쪽/왼쪽이 조금 밝고 아래쪽/안쪽이 어두운 방향을 기본으로 한다. 기존 참조와 반대 광원을 임의로 넣지 않는다. 불씨 같은 자체 발광은 별도 재질이다.
- 재질별 16단계 램프를 기준으로 설계하되 모든 면에 16색을 억지로 써야 하는 것은 아니다. 작은 아이콘도 색 수를 채우기 위한 점을 추가하지 않는다.
- 윤곽은 해당 재질의 어두운 색으로 정리한다. 잎은 짙은 녹색, 나무는 짙은 갈색이다. 어두운 눈구멍·틈은 허용하지만 전체를 두꺼운 순흑색 테두리로 감싸지 않는다.
- 고체 스프라이트는 기본적으로 알파 0/255. 배경 체크무늬, 키색, 흰 테두리, 반투명 색 번짐이 남으면 실패다. 연기·빛의 의도된 단계별 투명도는 별도다.
- 최종 스프라이트는 `nearest`. `linear`, 블러, 밉맵으로 빈약한 픽셀을 감추지 않는다. 제작 원화 처리나 별도 배경 타일의 기존 필터를 근거로 스프라이트 규칙을 바꾸지 않는다.

### 현재 실물 수치 — 모든 대상에 강제할 크기는 아니다

| 기준 대상 | 원생 그리드 / 파일 크기 | 표시·접점 기준 |
|---|---|---|
| 다람쥐·멧돼지·버섯 | 셀 128×128, 아틀라스 768×256 | 몸 너비 각각 33 / 49 / 43 월드 단위, 발선 120 |
| 덩굴괴수·사신 | 셀 160×160, 아틀라스 960×320 | 너비 57 / 58, 발선 152 |
| 엘더 트렌트 | 셀 256×256, 아틀라스 1536×512 | 너비 108, 발선 248 |
| 세계수 | 셀 320×320, 아틀라스 1920×640 | 너비 202, 발선 312 |
| 나무 | 활엽수 193×208 / 소나무 151×226 / 자작나무 144×216 / 단풍 170×226 | 현재 배율 1, 루트 앵커 `.91×높이` |
| 담배 | 256×48, 실제 사용 70색 | 길이 24 월드 단위의 장비, 프레임별 입 앵커 연결 |
| 담배 연기 | FX 그리드 192×384 | 월드 60×120, 축당 3.2 텍셀/월드 단위 |

현재 v3는 자산마다 8개 재질 램프×16단계 후보색을 만들고 필요한 색을 사용한다. 실제 사용색은 나무 46~101색, 적 66~100색이다. 담배의 70색은 품질 실물 기준이지 모든 이미지의 공통 색 수 하한이 아니다. 팔레트는 한 캐릭터의 프레임들에서 공유하며 서로 다른 대상을 한 팔레트에 억지로 맞추지 않는다.

**구체적인 계산 예:** 멧돼지 셀은 128이지만 몸 너비는 111픽셀이다. 표시 배율은 `49/111`, 기본 줌 .72에서 몸 너비는 `49×.72 ≈ 35` 화면 픽셀이다. 셀 너비 128로 나누면 투명 여백 때문에 크기가 달라진다. “128픽셀짜리 적이니 화면에서도 128픽셀”은 틀렸다. 메타데이터는 [forest_arcade_catalog.lua](../src/forest_arcade_catalog.lua)를 확인한다.

숫자만 같아도 그림이 다르면 실패다. 보스·건물·큰 장비를 작은 적의 셀에 억지로 우겨 넣지 않는다. 작은 아이콘에 보스 수준의 미세 묘사를 넣어 실제 크기에서 뭉개지게 만들지도 않는다.

## 5. 대상별로 유지할 것과 피할 것

| 대상 | 유지할 표현 | 피할 표현 |
|---|---|---|
| 나무·풀·바위 | 큰 덩어리, 종류별 실루엣, 적보다 조용한 세부 대비 | 잎/잔가지/금 간 선의 과밀 묘사, 사진 질감 |
| 일반 몬스터 | 작은 기존 비율, 읽히는 눈/입, 대표 특징 1~2개 | 임의의 거대화, 장식적인 새 판타지 종족, 과한 귀여운 마스코트화 |
| 보스 | 멀리서 식별되는 큰 형태와 공격 자세, 일반 적보다 충분한 제작 그리드 | 크기만 늘린 일반 적, 무수한 장식으로 위협감 대신하기 |
| 사람·주요 캐릭터 | 승인된 정체성·복장·장비, 다른 자산과 맞는 명암과 경계 | 요청 없이 얼굴·체형·복장 변경, 기존 사람을 전부 짧은 몸 마스코트로 바꾸기 |
| 건물·기계 | 큰 구조, 주요 기능 부품, 금속/목재 등 재질 차이 | CAD처럼 모든 볼트 묘사, 매끈한 3D 렌더를 그대로 삽입 |
| 장비·아이콘 | 실제 크기에서 보이는 핵심 형태와 재질 | 긴 장비를 몇 칸짜리 막대와 큰 사각형 불씨로 대체 |
| 불·연기·투사체 | 별도 픽셀 FX, 부착점/방출점, 크기에 맞는 세부 밀도 | 몸체에 FX를 구워 넣기, 불투명한 거대 원/네모로 표현 |
| 바닥·배경 | 캐릭터를 가리지 않는 대비, 반복 경계가 두드러지지 않는 무늬 | 바닥의 점과 풀을 몬스터보다 강하게 강조 |
| UI의 그림·아이콘 | 같은 재질·경계 성격, 작은 크기 가독성 | 숲과 무관한 매끈한 클립아트 삽입 |

텍스트·체력바·조준선 같은 기능 요소를 억지로 복잡한 텍스처로 만들 필요는 없다. 반대로 기능용 원/사각형을 캐릭터 몸·핵심 장비·완성된 연기 그림의 대체물로 쓰지 않는다.

## 6. 움직임과 게임 연결 규칙

1. 고정 모델의 몸·얼굴·장비·팔레트를 먼저 잠근다. 각 프레임마다 독립 생성해서 인상이 바뀌면 실패다.
2. 발선, 피벗, 투명 여백, 입/손 앵커, 원화의 기본 방향을 기록한다. 현재 몬스터는 6열×2행이지만 모든 FX·새 캐릭터를 무조건 같은 배열로 강제하지 않는다. 기존 플레이어 계약은 별도 기술 문서를 따른다.
3. 걷기는 발과 몸의 작은 움직임으로 표현한다. 모든 프레임이 같은 그림인데 타이머만 도는 것은 애니메이션이 아니다. 뿌리가 고정된 식물은 줄기/수관만 움직인다.
4. 좌우형 캐릭터는 실제 이동/액션 방향에 맞춰 그린다. 원화가 이미 왼쪽을 보는지 확인한다. 정면형 캐릭터는 정면 디자인을 유지할 수 있다. 멈출 때 방향이 불필요하게 튀지 않아야 한다.
5. 공격의 준비·접촉/발사·반동·회수와 실제 이벤트를 맞춘다. 그림을 개선하려고 피해·범위·공격 주기·이동속도를 몰래 바꾸지 않는다. 기존 즉시 공격에는 해당 이벤트의 반동을 붙일 수 있다.
6. 몸체는 나무·플레이어와 같은 지면 기준 정렬을 사용한다. 키 큰 그림의 위쪽 좌표나 HP바 좌표로 정렬하지 않는다. HP·전투 경고는 별도 레이어다.
7. 사용한 셰이더·색·블렌드 상태를 다른 오브젝트에 누출하지 않는다. 버전 파일만 만들고 런타임이 구버전을 읽는 상태를 “적용 완료”로 보고하지 않는다.

기존 담배 연기를 축당 3배 늘릴 때 그리드도 축당 3배 늘려 밀도를 유지한 것처럼, FX 확대 시 크기와 세부 밀도를 함께 다룬다. **연기의 3.2 텍셀/월드 단위를 모든 나무·UI까지 일괄 적용하는 규칙으로 오해하지 않는다.**

## 7. 실패 결과의 처리 방법

| 눈에 보이는 실패 | 조치 |
|---|---|
| 새 나무만 사실적으로 보인다 | 잎과 잔가지를 큰 덩어리로 다시 설계한다. 몬스터를 실사로 바꾸지 않는다. |
| 새 몬스터만 굵은 네모 조각처럼 보인다 | 원생 그리드에서 윤곽과 재질을 다시 작성한다. 블러를 켜지 않는다. |
| 확대하면 멋진데 게임에서는 안 보인다 | 실제 크기에서 핵심 특징의 대비·형태·비율을 정리한다. 확대 컷만 제출하지 않는다. |
| 다 같이 갈색 얼룩으로 보인다 | 재질/종류별 팔레트와 명도 차이를 회복한다. 전역 색조 필터로 통일하지 않는다. |
| 너무 장식적인 RPG 캐릭터가 됐다 | 승인된 작은 몸과 대표 특징으로 돌아간다. 팔레트만 바꿔 해결했다고 하지 않는다. |
| 몸체가 나무 위에 붙은 스티커처럼 보인다 | 지면 앵커·그림자·앞뒤 순서·윤곽 대비를 함께 확인한다. |
| 뒤를 보며 걷거나 담배가 입에서 떨어진다 | 프레임별 원화 방향·반전·앵커를 몸과 장비에 동일하게 적용한다. |
| 이미지 생성 도구가 없거나 원하는 결과가 안 나온다 | 한계와 미완료 범위를 알린다. 거친 도형 대체물을 몰래 최종본으로 납품하지 않는다. |

미채택 자료는 [enemies/README.md](../assets/enemies/README.md)에 명시되어 있다. `forest-enemies-concept-v1.png`, `forest-enemies-indie-concept-v2.png`, `ingame/*-atlas-pixel-v1.png`, `src/forest_enemy_catalog.lua`는 현재 기준으로 되돌릴 자료가 아니다. **다른 폴더의 모든 v1/v2를 일괄 금지하는 뜻은 아니다.** 현재 플레이어·담배 등의 유효한 v2는 그대로 사용한다. 구형 나무와 문자 그리드 몬스터 코드 역시 새 품질 기준이 아니다.

## 8. 작업 순서와 제출물

1. 참조 이미지와 현재 연결 코드를 읽고 대상·유지할 정체성·표시 크기를 적는다.
2. 같은 장면에 놓을 대표 자산 하나로 방향을 확인한다. 전체 스타일 변경이나 대량 신규 디자인이면 전량 교체 전에 사용자에게 시안을 보여준다. 이미 승인된 구체적 작업을 매번 재승인받을 필요는 없다.
3. 고정 모델을 정하고 원생 그리드·재질 램프·윤곽·알파를 제작한다. 생성 원화는 정체성 입력이며, 원화 한 장을 축소/양자화한 것만으로 품질 승인을 대신하지 않는다.
4. 같은 모델로 프레임과 앵커를 만들고 별도 FX를 연결한다. 원본/이전 버전은 보존하고 버전이 있는 새 파일을 쓴다.
5. 실제 런타임 로더·프레임 선택·셰이더·정렬 경로에 연결한다. 성능상 이미지와 쿼드를 매 프레임 다시 만들지 않는다.
6. 아래 자동 검사와 시각 검수를 실시한다. **사용자의 상시 지시에 따라 게임 창을 자동 실행하지 않는다.** 헤드리스/오프스크린 경로를 사용한다.
7. 파일/메타데이터/제작 소스/표시 크기 미리보기/확대 미리보기/동작 미리보기(해당 시)/검증 기록을 남긴다. 미검증 항목과 기존 실패를 구분한다.

## 9. 통과/실패 체크리스트

모든 항목을 검토한다. 해당하지 않는 항목은 이유를 적어 `N/A`로 표시한다. 미검증은 통과가 아니다.

- [ ] 실제 v3 기준 이미지와 비교했다. 기억 속 장르 스타일로 대신하지 않았다.
- [ ] 기본 표시 크기에서 대상 종류와 핵심 특징이 보인다.
- [ ] 나무·일반 적·플레이어 옆에 놓았을 때 혼자 다른 게임처럼 보이지 않는다.
- [ ] 큰 형태는 단순하고 내부 재질 명암은 충분하다. 원화의 작은 확대 복제나 무작위 노이즈가 아니다.
- [ ] 확대에서도 픽셀 경계·명암 단계·투명 윤곽이 정돈되어 있다.
- [ ] 어두운 배경과 밝은 배경에서 체크무늬·키색·흰 테두리가 없다.
- [ ] 실제 파일 크기, 알파, 팔레트, 프레임 수, 몸체 경계, 앵커를 확인했다.
- [ ] 걷기/정지/양방향/액션에서 정체성·장비·접점이 유지된다. 의도하지 않은 1픽셀 발선 오차도 고친다.
- [ ] 나무 앞/뒤에서 몸체의 순서가 맞고 HP·경고는 의도한 레이어에 있다.
- [ ] FX 크기·밀도·방출점이 요청과 맞고 핵심 대상을 가리지 않는다.
- [ ] 새 파일을 실제 로더가 사용한다. 구버전/미채택 파일을 계속 읽지 않는다.
- [ ] 변경한 셰이더는 실제 오프스크린 GPU에서 컴파일·렌더했다.
- [ ] 관련 회귀 검사를 수행했고 새 실패와 기존 실패를 구분했다.
- [ ] 그래픽 수정 때문에 전투 수치·범위·타이밍을 임의로 바꾸지 않았다.
- [ ] 게임 창을 자동으로 띄우지 않았고, 목업/오프스크린 렌더/엔진 캡처를 정확히 구분했다.

**자동 검사 통과 + 실제 크기 시각 검수 + 확대 시각 검수**가 필요하다. 파일의 해상도·색 수·테스트 결과 중 하나만으로 완성이라고 하지 않는다. 사용자가 원하는 외형과 다르면 검사 수치와 무관하게 다시 수정한다.

현재 숲의 재검증 예: `python scripts/verify_forest_arcade_assets.py`와 `python scripts/headless_lua.py scripts/verify_boss_sprites.lua`. 저장소 루트에서 실행하며 필요한 Python 라이브러리/Lua DLL은 [구현 기록](FOREST_ARCADE_ART.md)을 참고한다. 이것은 숲 검사이므로 새로운 UI·다른 FX까지 자동으로 검증해 주지는 않는다.

## 10. 다른 AI·이미지 도구에 전달할 문구

아래 문구만 보내지 말고 **실제 기준 이미지와 작업 대상**을 함께 전달한다. `TARGET` 등은 실제 값으로 바꾼다. 장비/표정/프레임은 요청하지 않은 것을 임의로 추가하지 않는다.

```text
Mandatory project style: match the supplied CURRENT v3 game render and asset
board. Read docs/GRAPHICS_STYLE_GUIDE.md before making or replacing graphics.
TARGET: [object and requested change]
KEEP: [identity, silhouette, proportions, equipment, existing behavior]
DISPLAY: [world or UI size, camera zoom, native grid, anchor requirements]

Use simple, readable cartoon silhouettes with carefully authored pixel
material shading inside them. Large coherent masses first; fine stepped
highlights and shadows second. Crisp pixel edges, restrained colored outlines,
material-specific palettes. Small arcade monsters keep their small proportions.
Trees use large foliage clusters and clear trunks, not individual realistic leaves.
High quality means better pixel structure, materials and motion, not realism,
more ornaments, higher PNG dimensions, or enlarged low-resolution blocks.

Do not use photorealism, smooth 3D/painterly rendering, flat vector stickers,
thick black strokes, random texture noise, ornate fantasy redesigns, or blur
to hide weak pixel art. Do not force every material into one forest palette.
Lock one model before animation; never independently generate each final frame.
Keep equipment anchors, source facing, feet and motion consistent. Separate FX.
Check the result beside the existing assets at actual gameplay size AND enlarged.
Preserve originals, version outputs, verify actual runtime loading. Never call
a concept mockup a game capture. Do not launch the game window for validation.
```

이 문구는 의미 전달용이다. 상세 규격·사용자 지시·실제 기준 이미지를 대체하지 않는다.
